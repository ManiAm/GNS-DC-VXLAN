
# Virtual Extensible LAN (VXLAN)

## The Prerequisite Concepts

### The Underlay Network (The Physical Foundation)

Before a virtual network can exist, there must be a physical path. The underlay is the actual, physical Layer 3 routed fabric: the cables, Top-of-Rack (ToR) leaf switches, and spine switches typically arranged in a Clos topology.

Unlike legacy networks that relied on Spanning Tree Protocol (STP) to block redundant paths and prevent loops at Layer 2, a modern underlay operates entirely at Layer 3. Every physical switch interface has an IP address, and dynamic routing protocols (like OSPF, IS-IS, or BGP) are used to build routing tables. This allows all links to be active simultaneously, providing massive bandwidth and redundancy via Equal-Cost Multi-Path (ECMP) routing. However, a pure Layer 3 network cannot natively transport Layer 2 MAC-address traffic across different subnets.

### The Overlay Network (The Virtual Illusion)

If the underlay is the physical highway system, the overlay is a series of dedicated, virtual tunnels built on top of those highways. The overlay allows isolated endpoints (like legacy servers or virtual machines) to believe they are residing on the exact same flat, Layer 2 network even if they are physically located in completely different server racks or geographic data centers.

The diagram below shows two separate planes: The physical underlay and the logical overlay. The bottom Underlay plane shows the actual physical infrastructure (a complex, routed mesh of interconnected switches and routers). The top Overlay plane represents the virtual network, demonstrating how a direct, logical tunnel (the red line) connects two edge devices across a virtual cloud. The vertical dashed lines illustrate how these virtual edge endpoints physically map down to the underlying hardware, highlighting how the overlay abstracts away the complex, multi-hop routing happening in the physical fabric beneath it.

### Encapsulation (MAC-in-UDP Tunneling)

To push flat Layer 2 traffic across a routed Layer 3 underlay, the network must use encapsulation. Encapsulation takes the original, standard Ethernet frame generated by a server and wraps it entirely inside a new UDP/IP packet. The physical underlay switches only read and route the outer IP headers; they are completely blind to the original payload inside.



## Understanding VXLAN

VXLAN creates a virtual Layer 2 network (overlay) on top of a physical Layer 3 network (underlay). Think of it as a tunnel that makes two distant switches believe they are directly connected at Layer 2. It is designed specifically to overcome the scaling and geographic constraints of traditional 802.1Q VLANs. VXLAN is standardized by the IETF in [RFC 7348](https://datatracker.ietf.org/doc/html/rfc7348) in 2014.


### The VNI: Solving the 4,096 Limit

Traditional VLANs use a 12-bit identifier, which hard-caps a network at 4,094 usable segments. In large-scale enterprise data centers or multi-tenant cloud environments, this address space runs out rapidly. VXLAN replaces the traditional VLAN ID with a **VXLAN Network Identifier** (VNI). The VNI utilizes a 24-bit field, which immediately expands the address space to over 16 million unique, isolated network segments. Network engineers can map thousands of legacy VLANs into thousands of unique VNIs, achieving virtually unlimited multi-tenant scalability.

### The VTEP: The Packaging Facility

Since the underlying physical network only routes IP packets, there must be a translation point where standard Layer 2 frames are packaged into VXLAN tunnels before crossing the fabric. This is handled by a **VXLAN Tunnel Endpoint (VTEP)**, which acts as the edge of the overlay network, performing the encapsulation (ingress) and decapsulation (egress) of VXLAN packets.

In a modern data center fabric, this role is usually fulfilled by a Hardware VTEP. A physical switch equipped with native VXLAN support. Encapsulation and decapsulation are performed directly in the hardware ASICs at full line rate, preventing latency or processing bottlenecks. This is typically deployed as a Top-of-Rack (ToR) leaf switch in a leaf-spine architecture. Operating at the fabric edge, the hardware VTEP performs two primary functions:

- **Downstream**: It connects to standard servers and compute nodes using traditional, untagged Ethernet or standard 802.1Q VLANs.
- **Upstream**: It connects to the spine switches via routed Layer 3 links.

The following diagram illustrates the dual nature of a VTEP. In the bottom Underlay plane, servers connect to physical Leaf switches, which route traffic through a mesh of Spine switches. As shown by the vertical mapping lines, those physical Leaf switches act as the VTEPs in the virtual plane above. In this top Overlay network, the VTEPs establish direct, logical tunnels to one another, completely abstracting away the multi-hop physical routing happening in the underlay fabric.

### The VTEP IP Address: The Tunnel Anchor

Every VTEP must have a dedicated, unique IP address to act as the permanent anchor point for its VXLAN tunnels. In a physical network switch, this is almost always configured as a Loopback interface. A Loopback is a logical, virtual interface inside the switch that never goes "down" as long as the switch is powered on. This provides a highly stable, always-on endpoint, ensuring that even if a specific physical cable gets unplugged, the tunnel remains active via redundant physical paths.

Once configured, this VTEP Loopback IP is injected into the underlay network's dynamic routing protocol (such as OSPF or BGP). By doing this, the routing protocol maps out the fabric, and every single spine and leaf switch learns exactly how to route traffic to that specific VTEP. Later, when the VTEP encapsulates a server's frame and builds the "Outer IP Header," it uses its own Loopback IP as the Source IP, and the remote VTEP's Loopback IP as the Destination IP.

### The VXLAN Frame Format

To achieve this tunneling, the VTEP takes the original Ethernet frame generated by the server and wraps it in a series of new headers before sending it across the physical network. This process is known as MAC-in-UDP encapsulation. The resulting VXLAN packet consists of the following layers:

<img src="../pics/vxlan_frame.png" width="500"/>

- Outer MAC Header (14 bytes)
  - **Destination MAC:** Next-hop MAC in the underlay (the router/switch toward remote VTEP).
  - **Source MAC:** Local VTEP's physical interface MAC.
  - **EtherType:** 0x0800 (IPv4) or 0x86DD (IPv6).

- Outer IP Header (20 bytes for IPv4)
  - **Source IP:** Local VTEP IP address.
  - **Destination IP:** Remote VTEP IP address.
  - **Protocol:** 17 (UDP).
  - **TTL:** Typically set to a high value (default varies by platform).
  - **DF bit:** Typically set (Do Not Fragment), requiring the underlay MTU to accommodate the overhead.

- Outer UDP Header (8 bytes)
  - **Source Port:** A hash of the inner frame's headers (src/dst MAC, src/dst IP, protocol). This provides entropy for ECMP load balancing in the underlay. The source port varies per flow, so underlay switches/routers can spread VXLAN traffic across multiple paths.
  - **Destination Port:** 4789 (IANA-assigned standard VXLAN port).
  - **Length:** Total length of UDP payload + UDP header.
  - **Checksum:** Set to 0x0000 (optional per RFC 7348; most implementations skip it for performance).

- VXLAN Header (8 bytes)
  - **Flags (8 bits):**
    - Bit 3 (I-flag): Must be set to 1 to indicate a valid VNI.
    - All other bits: Reserved, set to 0.
  - **VNI (24 bits):** VXLAN Network Identifier. Identifies the overlay segment.
    - Range: 0 to 16,777,215.
    - Analogous to VLAN ID but 24 bits instead of 12.

### MTU Considerations: Handling the Overhead

Whenever you encapsulate network traffic, you are essentially putting a box inside a slightly larger box. In the case of VXLAN, wrapping the original Layer 2 frame inside the Outer MAC (14 bytes), Outer IP (20 bytes), Outer UDP (8 bytes), and VXLAN (8 bytes) headers adds exactly 50 bytes of overhead to the total packet size. This creates an immediate physical constraint: if a server generates a maximum-size standard Ethernet frame of 1,500 bytes, the VTEP will swell that packet to 1,550 bytes before pushing it into the underlay fabric.

If the physical spine and leaf switches in the underlay are strictly configured for the default 1,500-byte Maximum Transmission Unit (MTU), they will see this new 1,550-byte packet as too large and instantly drop it (or attempt to fragment it, which severely degrades network performance). To successfully deploy VXLAN, network engineers must increase the MTU across the entire physical underlay network. The industry best practice is to enable Jumbo Frames on all physical switch ports typically setting the MTU to 9,000 or 9,216 bytes. This massive physical highway ensures the underlay can easily absorb the 50-byte VXLAN tax without dropping a single packet.

### Why is UDP used for VXLAN Encapsulation?

UDP is chosen for VXLAN encapsulation primarily to enable highly efficient load balancing across the physical underlay network. Modern leaf-spine fabrics rely on ECMP routing to distribute traffic across redundant links, and routers typically make these path decisions by hashing the outer network headers (the "5-tuple"). Because the outer IP addresses of a VXLAN tunnel between two VTEPs remain static, the ingress VTEP hashes the contents of the inner Layer 2 frame to dynamically generate a unique UDP source port for every distinct traffic flow. This injected entropy ensures that the underlay switches see constant variation in the outer headers, allowing them to evenly distribute the encapsulated virtual traffic across all available physical spine links without causing congestion, all while benefiting from the high-speed, stateless, and low-overhead nature of UDP.



## Step-by-Step: How a VXLAN Packet Travels

To understand VXLAN mechanics, let's track a single packet traversing a multi-rack data center. Assume Server A (Rack 1) wants to talk to Server B (Rack 2). Both servers are on the same subnet (e.g., 10.10.10.0/24) and believe they are on the same local network, but they are physically separated by a complex Layer 3 routed fabric.

### Step 1: Egress from the Server

Server A generates a standard Layer 2 Ethernet frame. The frame contains Server A's source MAC address, Server B's destination MAC address, and standard IP payload. Server A sends this untagged frame up the cable to its Top-of-Rack Leaf switch (leaf 1).

### Step 2: Encapsulation at the Ingress VTEP

The Leaf 1 switch (Ingress VTEP) receives the frame. It recognizes that this traffic belongs to a specific virtual network. The VTEP completely swallows the original frame and adds four new headers to create a VXLAN packet:

- **VXLAN Header**: Inserts the 24-bit VNI (e.g., VNI 50010) to identify the virtual network.
- **Outer UDP Header**: Adds a UDP header (Destination Port 4789, the standard port for VXLAN).
- **Outer IP Header**: Adds a new IP header. The Source IP is the Ingress VTEP (Leaf 1), and the Destination IP is the Egress VTEP (Leaf 2).
- **Outer MAC Header**: Adds a new MAC header to route the packet to the next-hop Spine switch.

> **Note:** You might wonder: *How does the Ingress VTEP (Leaf 1) know the IP address of the Egress VTEP (Leaf 2) that Server B is connected to?* At this stage, Leaf 1 only knows Server B's destination MAC address from the original frame. It needs a mechanism to map this inner MAC address to the correct outer VTEP IP address. This [Control Plane Problem](#the-control-plane-problem-how-do-vteps-find-each-other) is exactly what we will address in future section!

### Step 3: Transit Across the Underlay (The Spine)

The Ingress VTEP pushes the heavy, encapsulated packet into the Spine fabric.

- The Spine switches do not know or care about Server A or Server B.
- They do not look at the VNI.
- They only look at the Outer IP Header and route the packet at lightning speed toward Leaf 2 using standard IP routing (OSPF/BGP).

### Step 4: Decapsulation at the Egress VTEP

The packet arrives at Leaf 2 (the Egress VTEP). Leaf 2 looks at the Destination IP and realizes, "This packet is addressed to my VTEP interface!"

- It strips off the Outer MAC, Outer IP, UDP, and VXLAN headers.
- It looks at the inner, original Ethernet frame and sees the destination is Server B.

### Step 5: Delivery

Leaf 2 forwards the pure, original Layer 2 Ethernet frame down the local physical port to Server B. Server B receives the data completely unaware that it was just encapsulated and blasted across a Layer 3 routing fabric.





## The Control Plane Problem (How do VTEPs find each other?)

For the encapsulation process to work, the ingress VTEP (Leaf 1) has the server's original inner destination MAC and IP in hand, but it must figure out what to put in the **Outer Destination IP** field of the new VXLAN packet. To build this outer header, the network needs a way to map the inner destination MAC address to the physical IP address of the remote VTEP (Leaf 2) where the target server currently resides. There are two primary ways VXLAN handles this "Control Plane" mapping intelligence:

### Flood and Learn (The Legacy Way)

Originally, VXLAN used IP Multicast. If Leaf 1 didn't know where Server B was, it encapsulated the packet into a Multicast group and blasted it to every single VTEP in the network. Whichever VTEP had Server B would reply, and they would learn each other's locations dynamically. This is inefficient, wastes bandwidth, and mimics the exact broadcast storm issues we tried to escape with traditional VLANs.

### BGP EVPN (The Modern Standard)

In modern network operating systems, engineers pair VXLAN with **Ethernet VPN (EVPN)** using the Border Gateway Protocol (BGP). Instead of shouting across the network to find devices, VTEPs act intelligently. When a server plugs into a Leaf switch, the Leaf actively advertises that server's MAC and IP address to all other switches using BGP. Every switch maintains a localized, instantly updated database of exactly where every device lives in the fabric.

> VXLAN is the Data Plane (the muscle carrying the encapsulated packets), while BGP EVPN is the Control Plane (the brain telling the packets exactly which VTEP to route to).



## Handling "Chatty" Traffic Inside a VNI

In any traditional Layer 2 network (like a standard VLAN), devices rely heavily on sending messages to multiple devices at once to discover neighbors or announce their presence. This is collectively called **BUM Traffic**, which stands for:

- **Broadcast**: A message sent to every device on the network segment (e.g., an ARP request asking, "Who has IP address 192.168.1.5?").

- **Unknown Unicast**: A message intended for one specific device, but the network switch doesn't yet know which port that device is connected to. To ensure it reaches the destination, the switch "floods" the message out of all ports.

- **Multicast**: A message sent to a specific, subscribed group of devices (e.g., streaming video or routing protocol hellos).

In a traditional flat network, switches easily flood BUM traffic out of all their physical ports. However, in VXLAN the physical underlay network is built entirely of Layer 3 routers. By design, routers drop broadcast traffic to prevent network-wide broadcast storms. If a server in VNI 5000 sends an ARP request (Broadcast), the local VTEP needs to get that message to every other VTEP hosting VNI 5000. But it cannot simply broadcast it into the physical underlay, because the underlay routers will immediately kill it.

### The Solution: Ingress Replication

Ingress Replication (also known as Head-End Replication) is a method used to solve the BUM traffic problem over a routed Layer 3 network. Instead of relying on the physical network to broadcast the packet, the burden is placed on the Ingress VTEP (the edge switch where the traffic first enters the fabric). When the Ingress VTEP receives a BUM frame from a server:

- It looks at its internal table and identifies all the other remote VTEPs that are configured with that specific VNI.
- It makes a physical copy of the original packet for each of those remote VTEPs.
- It encapsulates each copy into a standard, point-to-point (Unicast) IP/UDP packet.
- It sends these individual unicast packets across the underlay.

Because the underlay routers see these as standard, one-to-one IP packets, they route them perfectly. Ingress replication is like sending an individual email to 10 different people, rather than using a single "reply-all" mailing list.



## Hosts in different VNIs require Layer 3 routing

Just like traditional VLANs, VNIs provide strict isolation. A host sitting in VNI 1000 cannot natively talk to a host in VNI 2000, even if they are physically plugged into the exact same ToR switch. They exist in parallel virtual universes. To allow communication between different VNIs, the traffic must be routed at Layer 3. This is analogous to [Inter-VLAN routing](./04_vlan.md#inter-vlan-communication) in legacy networks. Here is how the flow works when a server in VNI 1000 wants to talk to a server in VNI 2000:

- **Decapsulation**: The packet arrives at a routing gateway (this can be the local VTEP acting as a router, a core switch, or a firewall). The gateway strips off the VXLAN header for VNI 1000.

- **Routing**: The gateway looks at the destination IP address of the inner packet, checks its routing table, and routes the packet into the subnet associated with VNI 2000.

- **Re-encapsulation**: The packet is assigned the new VNI 2000 identifier, wrapped in a new UDP/IP VXLAN header, and sent across the underlay to the destination VTEP.

In modern VXLAN fabrics, this routing is often handled in a highly distributed manner right at the leaf switches (a concept called Anycast Gateway or Distributed Routing), ensuring traffic doesn't have to trombone up to a centralized core router just to jump between two VNIs.



## The Software VTEP (Host-Based Overlay)

If a Hardware VTEP stops the virtual overlay network at the physical network switch, a Software VTEP extends the virtual overlay all the way down into the server itself. Instead of relying on the physical network switch to package the traffic, the server's hypervisor handles the VXLAN encapsulation before the packet even touches the physical network cable.

- **Virtual Infrastructure**: The VTEP function is built directly into the hypervisor's virtual switch. Common examples include Open vSwitch (OVS), VMware vSphere Distributed Switch (VDS), or the native Linux kernel VXLAN implementation.

- **Performance**: Encapsulation and decapsulation are performed entirely by the host server's CPU. Modern network interface cards, or SmartNICs, often provide "hardware offloading" to help the CPU process this math without degrading server performance.

- **Topology Placement**: In this model, every single physical server running virtual machines (VMs) or containers acts as its own independent VTEP.

When using a Software VTEP, the ToR Leaf switch is no longer acting as the translation point.

- A VM generates a standard Layer 2 Ethernet frame.

- The hypervisor (Software VTEP) immediately intercepts it and wraps it in the VXLAN UDP/IP header.

- The server sends the fully encapsulated VXLAN packet out of its physical network port.

- The physical ToR switch receives the packet. Because it is already an IP packet, the physical switch simply routes it across the underlay fabric like any other normal traffic. The physical network has zero awareness of the VXLAN overlay; it just routes IP addresses.

This approach is highly popular in heavily virtualized environments (like VMware NSX or complex OpenStack deployments) because it gives server administrators complete control over the virtual network without needing to reconfigure the physical network switches.

## 1. The Problems VXLAN Solves

Traditional VLANs have limitations that become critical in modern data center and cloud environments. VXLAN was designed to address these specific problems:

### Problem 1: VLAN ID Exhaustion (4,094 VLAN Limit)

The 802.1Q VLAN ID is 12 bits, allowing only 4,094 usable VLANs. In a multi-tenant cloud data center with thousands of customers, each needing isolated network segments, this limit is quickly exhausted.

**VXLAN solution:** A 24-bit VXLAN Network Identifier (VNI) supports up to 16,777,215 (~16 million) unique segments.

### Problem 2: Spanning Tree Limitations

VLANs rely on Spanning Tree Protocol (STP) to prevent Layer 2 loops. STP works by blocking redundant links, which means:
- Not all available bandwidth is utilized.
- A triangle of three switches will have one link blocked.
- Failover can take seconds, disrupting traffic.

**VXLAN solution:** The underlay is a routed Layer 3 network. Routing protocols (OSPF, BGP) use Equal-Cost Multi-Path (ECMP) to load-balance across ALL available links simultaneously. No links are blocked. Convergence is sub-second.

### Problem 3: Geographic Limitation

VLANs require Layer 2 adjacency -- all switches must be connected via trunk links in a flat L2 domain. Extending a VLAN across data centers requires complex L2 extension technologies (OTV, VPLS).

**VXLAN solution:** VXLAN tunnels traverse any IP network. Two hosts can be in the same Layer 2 segment even if separated by multiple routers and geographic distances. As long as IP connectivity exists between the tunnel endpoints, the overlay works.

### Problem 4: MAC Address Table Scalability

In a large flat L2 network, every switch must learn the MAC address of every host. A data center with 100,000 VMs means 100,000 MAC entries on every switch in the domain.

**VXLAN solution:** The underlay switches (spine/leaf) only see the outer IP/MAC headers (the VTEP addresses). They do not learn individual VM MAC addresses. MAC learning is confined to the VTEPs at the edge.

### Problem 5: VM Mobility

In virtualized environments, virtual machines (VMs) migrate between physical hosts (potentially in different racks or even data centers). The VM must keep its IP address and Layer 2 identity. Traditional VLANs require L2 connectivity between the source and destination hosts.

**VXLAN solution:** As long as both physical hosts have a VTEP and IP reachability, a VM can be moved transparently. The overlay maintains L2 connectivity regardless of the physical location.

## 7. VXLAN Packet Walk-Through

**Scenario:** Host-A (MAC: AA:AA, IP: 10.0.1.10, VNI: 5000) wants to send a frame to Host-B (MAC: BB:BB, IP: 10.0.1.20, VNI: 5000). Host-A is connected to VTEP-1 (IP: 192.168.1.1). Host-B is connected to VTEP-2 (IP: 192.168.1.2).

### Step 1: Host-A generates original frame

```
[Dst: BB:BB | Src: AA:AA | Type: 0x0800 | IP Payload | FCS]
```

### Step 2: Frame arrives at VTEP-1

- VTEP-1 receives the frame on a port mapped to VNI 5000.
- VTEP-1 looks up destination MAC BB:BB in its MAC table for VNI 5000.
- Finds: BB:BB is reachable via VTEP-2 at 192.168.1.2.

### Step 3: VTEP-1 encapsulates

- Prepends VXLAN header: VNI = 5000, I-flag = 1.
- Prepends UDP header: Src port = hash(AA:AA, BB:BB, ...), Dst port = 4789.
- Prepends IP header: Src = 192.168.1.1, Dst = 192.168.1.2.
- Prepends Ethernet header: Src = VTEP-1 MAC, Dst = Next-hop router MAC.
- Recalculates outer FCS.

### Step 4: Packet traverses the underlay

- Underlay routers forward based on outer destination IP (192.168.1.2).
- ECMP may spread traffic across multiple paths based on the outer UDP source port.
- Underlay devices have NO visibility into the inner frame.

### Step 5: Packet arrives at VTEP-2

- VTEP-2 receives the packet on UDP port 4789.
- Validates VXLAN header: I-flag = 1, VNI = 5000.
- Strips outer Ethernet + IP + UDP + VXLAN headers.
- Learns: MAC AA:AA is behind VTEP-1 (192.168.1.1) in VNI 5000.

### Step 6: VTEP-2 delivers original frame to Host-B

- VTEP-2 looks up destination MAC BB:BB in its local table for VNI 5000.
- Finds Host-B on local port.
- Sends the original unmodified L2 frame to Host-B.

Host-B receives the frame exactly as Host-A sent it -- completely unaware of the VXLAN tunnel in between.

## 8. BUM Traffic Handling (Broadcast, Unknown Unicast, Multicast)

In a traditional L2 network, BUM traffic is flooded to all ports in the VLAN. In VXLAN, there is no shared L2 medium -- the VTEPs are separated by an L3 network. So how does BUM traffic reach all hosts in the same VNI?

Three approaches:

### 8.1 Multicast-based Flooding

- Each VNI is mapped to an IP multicast group in the underlay.
- When a VTEP needs to flood a frame (BUM), it encapsulates it and sends it to the multicast group address.
- All VTEPs that have joined that multicast group receive the packet.
- Requires multicast (PIM) enabled in the underlay.

**Advantage:** Efficient -- only VTEPs with interested hosts receive the traffic.

**Disadvantage:** Requires multicast support in the underlay (complex to configure and operate).

### 8.2 Ingress Replication (Unicast-based)

- The source VTEP replicates the BUM frame and sends a separate unicast copy to EACH remote VTEP that has hosts in the same VNI.
- No multicast required in the underlay.
- The source VTEP must know the list of all remote VTEPs for each VNI.

**Advantage:** No multicast needed; simpler underlay.

**Disadvantage:** More bandwidth consumption at the source VTEP (N copies for N remote VTEPs). Works well for small-to-medium deployments.

### 8.3 BGP EVPN (Control-Plane Learning)

- BGP EVPN advertises MAC addresses and their associated VTEPs proactively.
- VTEPs learn remote MACs via BGP updates BEFORE any data traffic is sent.
- BUM flooding is minimized or eliminated for known unicast traffic.
- ARP/ND suppression: The VTEP answers ARP requests locally from its EVPN-learned database, preventing ARP broadcasts from being flooded.
- This is the modern, recommended approach. See 06_evpn.md for details.

## 9. VXLAN Control Plane Options

The "control plane" determines how VTEPs discover each other and learn which MAC addresses are behind which VTEP.

### 9.1 Multicast-Based (Flood and Learn)

- **Discovery:** VTEPs join a multicast group associated with each VNI.
- **Learning:** Data-plane learning. When VTEP-2 receives an encapsulated frame from VTEP-1, it learns the source MAC and the source VTEP IP.
- **BUM handling:** Encapsulated into multicast packets.
- **Requires:** PIM-SM or PIM-BiDir in the underlay, plus a Rendezvous Point (RP).
- This was the original VXLAN model from RFC 7348.

### 9.2 Unicast-Based (Static or Ingress Replication)

- **Discovery:** VTEP peer lists are statically configured, or learned via a controller.
- **Learning:** Data-plane learning (same as multicast model).
- **BUM handling:** Head-end replication (ingress replication).
- **Requires:** Only unicast IP reachability in the underlay.

### 9.3 BGP EVPN (Ethernet VPN) -- Recommended

- **Discovery:** VTEPs are BGP peers. They advertise their VNI memberships.
- **Learning:** Control-plane learning via BGP. MAC/IP routes are advertised.
- **BUM handling:** Ingress replication lists are built automatically from BGP routes.
- **Requires:** BGP (iBGP with route reflectors, or eBGP in spine-leaf).
- This is the industry-standard approach for production deployments.
- Full explanation in 06_evpn.md.

## 10. VXLAN Gateway Types

A VXLAN gateway connects the VXLAN overlay to external networks or provides routing between different VNIs.

### 10.1 Layer 2 Gateway (Bridging)

Bridges traffic between a traditional VLAN and a VXLAN VNI.

**Use case:** Connecting a bare-metal server (on a traditional VLAN) to VMs in a VXLAN segment.

The gateway maps: VLAN 10 <--> VNI 10010. Frames arriving on VLAN 10 are encapsulated into VXLAN with VNI 10010 and vice versa.

### 10.2 Layer 3 Gateway (Routing)

Routes traffic between different VNIs (analogous to inter-VLAN routing).

**How it works:**
- Each VNI is mapped to a subnet on the gateway.
- The gateway has an SVI in each VNI.
- Packets arriving in VNI 5000 destined for a host in VNI 6000 are routed by the gateway (TTL decremented, new L2 header, re-encapsulated with VNI 6000).

This can be:
- **Centralized:** One or two dedicated border leaf switches perform all inter-VNI routing.
- **Distributed:** Every leaf VTEP performs routing locally (preferred for performance).

### 10.3 Distributed Anycast Gateway

In a distributed model, EVERY leaf VTEP acts as the default gateway for its local hosts.

**How it works:**
- All leaf VTEPs for a given VNI share the SAME gateway IP and virtual MAC address.
- From the host's perspective, the default gateway is always "one hop away" regardless of which leaf it is connected to.
- When a host sends traffic to a remote subnet, its local leaf routes it immediately (no need to hairpin to a centralized gateway).

**Benefits:**
- Optimal routing (no traffic tromboning through a central node).
- Seamless VM mobility (the gateway IP/MAC stays the same on any leaf).
- High availability (no single point of failure).

This requires a symmetric IRB (Integrated Routing and Bridging) model where each VTEP can both bridge (L2) and route (L3) for any VNI.

## 11. L2 VNI vs. L3 VNI

Understanding the difference between L2 VNI and L3 VNI is essential for VXLAN routing:

### L2 VNI (Layer 2 VNI)

- Maps to a specific VLAN/subnet.
- Carries bridged traffic (same subnet) between VTEPs.
- Each VLAN on a leaf gets its own L2 VNI.
- Example: VLAN 100 (10.100.1.0/24) maps to VNI 10100.

### L3 VNI (Layer 3 VNI)

- Maps to a VRF (Virtual Routing and Forwarding instance).
- Carries routed traffic (different subnets) between VTEPs.
- One L3 VNI per tenant/VRF, regardless of how many subnets exist.
- Example: Tenant-A VRF uses L3 VNI 50000. All inter-subnet traffic for Tenant-A is encapsulated with VNI 50000 when crossing VTEPs.

### How They Work Together

1. Host-A (10.100.1.10, VLAN 100, L2 VNI 10100) wants to reach Host-B (10.200.1.20, VLAN 200, L2 VNI 10200) on a different leaf.
2. Host-A sends to its local gateway (leaf-1 SVI for VLAN 100).
3. Leaf-1 routes the packet from VLAN 100 to VLAN 200 (different subnets).
4. Leaf-1 encapsulates with the L3 VNI (50000) and sends to leaf-2.
5. Leaf-2 decapsulates, performs the final L2 lookup in VLAN 200, and delivers to Host-B.

## 12. VXLAN in Spine-Leaf Data Center Architecture

Modern data centers use a spine-leaf (Clos) topology for the underlay:

```
     [Spine-1]     [Spine-2]
       |    \       /    |
       |     \     /     |
       |      \   /      |
     [Leaf-1]  [Leaf-2]  [Leaf-3]  [Leaf-4]
       |          |          |          |
     Hosts      Hosts      Hosts      Hosts
```

**Characteristics:**
- Every leaf connects to every spine (full mesh between tiers).
- Hosts connect only to leaf switches.
- Spine switches perform only IP forwarding (no host-facing ports).
- All leaf-to-leaf traffic traverses exactly one spine (two hops).
- ECMP across all spine links provides maximum bandwidth utilization.

**Where VXLAN fits:**
- Leaf switches = VTEPs (perform encap/decap).
- Spine switches = IP routers (forward outer IP packets, unaware of VXLAN).
- BGP EVPN runs between leaves (via spine as route reflector or eBGP peer).
- Hosts see a flat L2 network despite the routed underlay.

**Benefits:**
- Predictable latency (always two hops leaf-spine-leaf).
- Linear scalability (add spines for bandwidth, add leaves for ports).
- All links active (no STP blocking).
- Any host can be in any VNI regardless of physical location.

## 13. VXLAN vs. VLAN Comparison

| Feature | VLAN (802.1Q) | VXLAN |
|---------|---------------|-------|
| Identifier size | 12 bits (4,094) | 24 bits (16,777,215) |
| Encapsulation | 4-byte 802.1Q tag | 50-byte outer headers |
| Network layer | Layer 2 only | L2 overlay over L3 underlay |
| Geographic scope | Single L2 domain | Any IP-reachable distance |
| Loop prevention | STP (blocks links) | L3 routing + ECMP (all active) |
| Bandwidth utilization | Suboptimal (STP) | Optimal (ECMP, all paths used) |
| MAC table scope | All switches in VLAN | Only VTEPs at the edge |
| VM mobility | Limited to L2 domain | Unlimited (any IP reachable VTEP) |
| Control plane | STP | BGP EVPN |
| Multi-tenancy | 4,094 tenants max | ~16M tenants |
| MTU overhead | 4 bytes | 50 bytes |
| Underlay requirement | L2 switched network | IP routed network |
| Complexity | Low | Higher (requires IP fabric + BGP) |
| Typical use case | Enterprise campus LAN | Data center, cloud, multi-tenant |

---

## 14. Summary

VXLAN solves the critical limitations of traditional VLANs:

| VLAN Limitation | VXLAN Solution |
|-----------------|----------------|
| 4,094 segment limit | 16 million+ segments (24-bit VNI) |
| STP blocks redundant links | L3 underlay uses ECMP (all links active) |
| Limited to single L2 domain | Spans any IP network (data center, WAN) |
| All switches learn all MACs | MACs confined to VTEPs at the edge |
| VM mobility restricted | VMs migrate freely between any VTEPs |
| No standard control plane | BGP EVPN provides scalable control plane |

VXLAN + BGP EVPN is the industry standard for modern data center network fabrics. The control plane (EVPN) is explained in 06_evpn.md, and a complete hands-on lab using SONiC is provided in 07_lab.md.
